## 1. 背景与问题

JOTO 的 GEO 监测首期实测结论：**品牌词 SOV 83.3%，需求侧词 SOV 0.0%**。

意思是——知道「上海聚托」这个名字的人能搜到我们，但一个正在问「国内 AI 文档解析哪家好」的潜在客户，在 AI 里完全看不到我们。

根因不在官网（可达性通），在于**需求侧问句上没有可被引用的第三方内容**。而建设这类内容，卡在一个很土的环节：**写完稿子要人肉登录平台、排版、传图、点发布**，一个人一天发不了三篇，且容易漏、容易重、容易错。

**所以本需求的本质是：把「有稿子」到「稿子上线」之间的人工动作自动化，让内容供给的产能不再受人力限制。**

## 2. 目标与非目标

### 2.1 目标（按优先级）

| 优先级 | 目标 | 衡量方式 |
|---|---|---|
| G0 | 建产品库：产品资料一次入库，成为所有成稿的唯一素材来源 | 入库后可被成稿层直接引用，无需人工整理 |
| G1 | 从产品库自动产出可发布的稿件 | 产出稿件通过 §4 全部自检项 |
| G2 | 每个工作日定时自动发布，**人只验收结果** | 连续 5 个工作日无人干预，每天有发布记录或明确失败原因 |
| G3 | 发布行为可追溯、不重复、可回溯 | publish-log 完整，重复执行被拦截 |
| G4 | 发布结果能被现有监测系统识别为自有渠道 | 下期监测 cited 能判定 |
| G5 | 选题决策串联 geo-master，不自建第二套优先级逻辑 | 每日选题可回溯到 gap_prioritizer 的输出 |

### 2.2 非目标（本期明确不做）

| 不做 | 原因 |
|---|---|
| 不自建选题算法 | 选题复用 geo-master 的 `gap_prioritizer`（缺口×商业价值/可达性/可赢性/成本），本引擎只负责喂数据和执行结论 |
| 不做 AI 可见度采集 | 属 geo-monitor 职责 |
| 不做多账号 / 矩阵运营 | 合规红线，平台判定为营销号直接限流 |
| 不做验证码绕过 | 合规红线，且技术上不成立 |
| 不做洗稿 / 伪原创 | 合规红线（T/CAPT 026—2026） |
| 一期不做掘金 | 掘金营销审核更严，需 CSDN 跑通后再评估 |
| 不承诺「发布后一定被 AI 引用」 | 发布只是必要条件，不是充分条件 |
| 不承诺「完全无人值守」 | 遇验证码/登录失效会停在当日日报里等人，这是风控边界不是缺陷 |

## 3. 用户与使用场景

### 3.1 用户

| 角色 | 是谁 | 关心什么 |
|---|---|---|
| 内容负责人 | 拾一米 | 稿子对不对、发没发出去、有没有发重 |
| 执行系统 | 本 skill | 按规则执行，遇异常停下 |

### 3.2 典型场景

**场景 A · 产品库日常运营（主场景）**

拾一米把产品资料丢进产品库 → 此后不再过问内容生产。每个工作日定时，系统自动完成：

```
选题（geo-master gap_prioritizer 决定今天写什么）
  → 从产品库取事实 → 成稿 → 合规自检
  → 定时发布到各平台 → 回执落盘
  → 产出当日发布日报
```

**拾一米每天要做的只有一件事：打开日报，确认「发出去了没有」。**

**场景 B · 手动补充投递（辅助）**
临时有一篇想马上发的稿（如热点跟进），手动触发单篇流程，不等定时。

**场景 C · 异常处理**
日报里某篇标了 `needs_human`（验证码/登录失效/审核拒绝）→ 看截图和原因 → 处理（扫码/改稿）→ 次日自动恢复。

### 3.3 使用前置条件（**硬前提，不满足则整个方案不成立**）

| # | 条件 | 状态 |
|---|---|---|
| P1 | CSDN 账号已注册且**已完成实名认证** | 待确认 |
| P2 | 账号处于可正常发文状态（未被限流/封禁） | 待确认 |
| P3 | 有可用的产品资料（PPT/文档/官网链接） | 待提供 |
| P4 | 本机可运行 Chrome（已验证 Chrome 155 存在） | ✅ |

> **P1 是硬卡点**：CSDN 未实名认证的账号不能正常发文，也不能进推荐。如果账号是新注册未实名的，第一步应该是去实名，而不是跑自动化。

## 4. 功能需求与验收标准

> 编号规则：`R` = 功能需求。每条都必须能被判定「过 / 不过」。
> 无法判定的需求不写进本文档。

### 4.1 输入与成稿

**R1 · 资料解析为事实清单**
- 输入：一份资料（PPT / Word / PDF / 网页链接 / 纯文本）
- 输出：`facts.json`，每条含 `claim`、`source`（页码/段落/URL）、`tier`（A/B/C/D）、`date`
- **验收**：给定一份 ≥15 页的产品资料，抽取 ≥12 条可引用事实；**`source` 为空的事实数必须为 0**；抽取内容不含资料外的信息（人工抽检 5 条，0 条越界）

**R2 · 锚定单一问句**
- 输入：`geo-monitor/config/joto.json` 的 `queries`
- 输出：`brief.json` 含 `anchor_query_id`
- **验收**：`anchor_query_id` 有且仅有 1 个；该 id 在 config 中存在；该问句属于 C/D/S 类（需求侧），不接受 B/P 类品牌词（因为品牌词已 83% 覆盖，做它没有增量）

**R3 · 生成 CSDN 版稿件**
- 输出：`csdn.md`
- **验收**：同时满足下列 6 条——
  1. 开头 ≤80 字内直接回答锚定问句（结论前置）
  2. H2 小标题 ≥3 个，且为问句形式
  3. 每个二级章节 200–400 字，可独立成块被引用
  4. 全文 3000–5000 字
  5. 结尾 FAQ ≥3 条
  6. 品牌与产品实体在文中出现 ≥3 次，且使用统一全称

**R4 · 合规自检（硬闸门）**
- 输出：`selfcheck.json`（含每项检查的命中明细）
- **验收**：下列任一不满足，稿件状态置 `rejected`，**不得进入发布队列**——
  1. 绝对化用语命中数 = 0（最好/第一/唯一/领先/顶级/保证/100%/绝对/永久）
  2. 营销句式命中数 = 0（欢迎咨询/联系我们/立即购买/扫码添加/免费试用）
  3. 数字类主张的 `source` 覆盖率 = 100%
  4. 标题长度在平台限制内，标签数在平台限制内
  5. AI 参与度字段已填写（`human` / `assisted` / `generated`）

**R5 · 封面图生成**
- 输出：`cover.png`，尺寸符合平台后台上传框实际要求
- **验收**：封面无错别字（人工看一次通过）；标题文字可单独修改而**不需要重新生成主视觉**；文件大小在平台限制内

### 4.2 登录与会话

**R6 · 登录态持久化**
- **验收**：扫码登录一次后，**连续 7 天内**无需再次扫码即可发布；登录态失效时，命令**退出码 = 2** 并输出「需重新授权：<具体命令>」，且**不发起任何自动重试**

### 4.3 发布执行

**R7 · 草稿投递（P0 里程碑）**
- 输入：`csdn.md` + `meta.json` + `cover.png`
- **验收**：执行命令后，CSDN 后台「草稿箱」出现该文章；标题、正文、分类、标签、封面均正确；**正文与源文差异 < 2%**（字符级比对）

**R8 · 全自动发布（P1 里程碑）**
- **验收**：给定一篇通过 R4 自检的稿件，执行**一条命令**，**5 分钟内**产出可公开访问的 `https://blog.csdn.net/<账号>/article/details/<id>`；该 URL 用无痕窗口打开可看到正文

**R9 · 幂等（防重发）**
- **验收**：同一篇稿件连续执行两次，第二次输出 `SKIPPED_DUPLICATE`，平台侧该文**只有 1 篇**；进程在提交瞬间被强杀后再执行，状态为 `needs_human` 而**不是**自动重发

**R10 · 回执落盘**
- **验收**：每次运行在 `data/runs/<ts>/` 留下 `receipt.json`（url/article_id/published_at/status）与 `before.png`、`after.png` 两张截图；`publish-log.csv` 追加一行且字段完整

### 4.4 闭环

**R11 · 监测回填**
- **验收**：发布成功后，`geo-monitor/config/joto.json` 的 `owned_channels` 含 `{"domain": "blog.csdn.net", "path_hint": "/<账号>"}`；下一期监测中，若该文章 URL 出现在某问句的检索结果里，`cited` 判定为 `true`（而非降级判定）

### 4.6 产品库与每日自动运营（v1.2 新增）

**R15 · 产品库**
- 输入：产品资料（PPT / Word / PDF / 网页链接），一次或分批
- 输出：`data/products/<product_id>/` 下 `facts.json`（事实+出处+等级）、`qa.json`（该产品可锚定的问句映射）
- **验收**：
  1. 入库后**无需任何人工整理**即可被 R1–R3 成稿流程引用
  2. 同一产品二次入库是**合并更新**而非覆盖（旧事实保留原出处）
  3. 产品库内容可追溯：任一事实能指回原始资料的位置

**R16 · 每日定时调度**
- 输入：发布时间表（默认工作日 10:00，可配置多平台错峰，如 CSDN 10:00 / 掘金 15:00）
- **验收**：
  1. 连续 **5 个工作日**无人干预，每天要么产出一篇已发布文章，要么在日报里给出带原因的失败记录
  2. **不允许静默失败**：进程没跑、跑挂了、平台拒绝了，三种情况都必须体现在当日日报里
  3. 节奏约束（R14）在自动调度下依然生效

**R17 · 选题串联 geo-master**
- 机制：调度器每日组装缺口清单（geo-monitor 缺口 + 产品库问句矩阵），调用 `geo-master/scripts/gap_prioritizer.py` 的 `prioritize()` 得到 P0–P3 档位，**只写 P0/P1 档的选题**
- **验收**：
  1. 每日选题可回溯到当日的缺口输入和优先级打分
  2. 「同问句 × 同平台」30 天内不重复（除非配置显式允许翻新）
  3. 问句口径与 `geo-monitor/config/joto.json` 同源，不另建问句表

**R18 · 每日发布日报（拾一米的唯一检查入口）**
- 输出：`data/reports/<date>.md`，并**每日推送到指定邮箱**
- **验收**：日报必须能独立回答以下四问，且**只需看这一份文件**——
  1. 今天该发几篇？实发几篇？
  2. 每篇的平台、标题、URL（可直接点开）
  3. 失败的：失败在哪一步、平台原话、截图路径
  4. 明天会发什么（预告，可提前喊停）
- **推送要求**：
  1. 邮件主题行即结论，格式 `[JOTO GEO] MM-DD 发布 X/Y · 平台名`
  2. **推送失败不得影响发布状态判定**：稿件已发布但邮件未送达时，发布状态仍为 `published`，推送状态单独记为 `notify_failed`
  3. 异常告警（`needs_human`、连续两日零发布）走即时通道，与日报分开

**R18.1 · 干预通道（v1.3 新增）**

日报里的「明日待发」必须能被干预，否则“检查”只是看热闹。

**发布节奏改为两阶段**（关键：稿子必须提前一天生成，才有可干预的窗口）

```
T 日 10:00   选题 → 成稿 → 自检 → 入队（queued）
             日报列出「明日待发：标题 + slug」
T 日 全天    人工干预窗口
T+1 日 10:00 只发布状态仍为 queued 的稿件
```

**三种干预**

| 操作 | 命令 | 效果 |
|---|---|---|
| 暂停单篇 | `geopublish hold <slug>` | 状态 → `held`，次日跳过 |
| 编辑单篇 | `geopublish edit <slug>` → `recheck <slug>` | 自检通过才恢复 `queued` |
| 全局暂停 | `geopublish pause --until <date>` | 期间全部跳过，到期自动恢复 |

**验收**
1. `held` 状态的稿件次日**不被发布**
2. 稿件被编辑但**未重新自检** → 不得发布（防绕过 R4 闸门）
3. `pause --until` 到期后自动恢复发车，无需人工解除
4. 每次干预写入日志：谁、何时、对哪篇、做了什么（N4 可追溯的补充）

### 4.7 异常与风控

**R12 · 失败可诊断**
- **验收**：任一步失败时，run 目录内有失败截图、失败阶段标识、平台原始提示文本；日志能直接看出停在第几步

**R13 · 遇风控即停（红线）**
- **验收**：页面出现滑块/点选验证时，进程结束、状态 `needs_human`、保留截图；**全程无任何绕过尝试**（代码审查确认不存在验证码处理逻辑）

**R14 · 发布节奏控制**
- **验收**：同一平台 24 小时内发布数超过配置阈值（默认 1）时，拒绝执行并提示；阈值可在配置中修改

## 5. 非功能性需求

| # | 要求 |
|---|---|
| N1 | 单篇发布总耗时 < 5 分钟（不含平台审核等待） |
| N2 | 登录凭据目录权限 700，不纳入版本控制，不进任何云同步目录 |
| N3 | 平台选择器不得硬编码在主逻辑中（改版时只改配置文件） |
| N4 | 所有产物可追溯：任一 URL 能回溯到源资料、稿件、执行日志 |
| N5 | 失败不产生副作用：失败不得留下半成品草稿（或必须显式标注为失败残留） |
| N6 | 实现语言与现有技能一致（Python），不引入第三套运行时 |

## 6. 用户操作序列（实际怎么用）

**首次（一次性）**
1. 完成 CSDN 实名认证
2. 执行登录命令，手机扫码
3. 提供产品资料，系统建产品库
4. 确认发布时间表与节奏阈值

**日常（每天）**
1. **看日报**（约 1 分钟）：今天发了什么、URL、有没有失败的
2. 丢新资料进产品库（有新材料才做，没有就不用管）

**异常时（日报里标 `needs_human` 的）**
- 扫码重新授权（登录过期）
- 按日报里的平台原话改稿
- 处理完次日自动恢复，无需额外操作

**只有 3 类动作需要人**：首次扫码、日常看日报、处理异常。内容生产和发布全程无人干预。

## 7. 验收方式

| 阶段 | 测什么 | 通过标准 |
|---|---|---|
| P0 | 一条命令让 CSDN 草稿箱出现正确文章 | R6 + R7 全过 |
| P1 | 一条命令拿到公开 URL，且复跑不重发 | R8 + R9 + R10 全过 |
| P2 | 给产品库资料能出稿且过自检 | R1–R5 全过 |
| P3 | 产品库 + 每日调度 + 日报闭环 | R15–R18 全过：连续 5 个工作日无人干预，每天有日报 |
| P4 | 监测回填 | R11 全过（掘金整体归入二期计划，不在本期） |

**任一阶段不达标，停在该阶段修，不向下推进。**

## 8. 风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| **无人过稿，错稿直发** | 品牌声誉（v1.2 主场景固有风险） | R4 自检是唯一事前闸门，不得弱化；日报带每篇标题+首段摘要，拾一米扫一眼即异步抽查；发现问题当日可下架重写 |
| 自动选题写出与产品无关的内容 | 浪费发布配额 | R17 选题必须能映射到产品库事实，映射不上则当日跳过并记录 |
| CSDN 编辑器改版 | 发布失败 | 选择器外置；失败自动截图定位 |
| 新号触发验证码 | 当日发布中断 | 停下转人工（R13），日报体现，次日恢复 |
| 新号被判营销号限流 | 内容白发 | 节奏控制（R14），前两周每天 ≤1 篇 |
| 稿件事实无出处 | 合规与信任风险 | R4 硬拦截，无出处不进稿 |
| 发布 ≠ 收录 ≠ 引用 | 业务预期错位 | 本文档 §2.2 已明确不承诺 |

**依赖**：geo-monitor 的 `owned_channels` 结构升级（R11），这是本需求唯一需要改动现有系统的点。

## 9. 变更影响域（每部分能改什么、改了会波及谁）

### 9.1 三级变更分级

| 级别 | 改什么 | 谁改 | 需重新评审 | 波及 |
|---|---|---|---|---|
| **L1 配置级** | 阈值、标签、尺寸、频率、词表、问句 | 你直接改 | 否 | 只影响下一篇稿 |
| **L2 适配级** | 平台选择器、字段映射、步骤顺序 | 我改，你验结果 | 否 | 只影响该平台 |
| **L3 架构级** | 数据模型、接口契约、状态机、闸门规则 | 必须先评审 | 是 | 全平台 + 监测对接 |

**判定口诀**：改动只影响「这一篇」是 L1，只影响「这个平台」是 L2，影响「别的平台或监测」是 L3。

### 9.2 模块边界

| 模块 | 职责 | 可改范围 | 红线（不许碰） |
|---|---|---|---|
| `write/` 成稿 | 资料 → 稿件 | 结构模板、字数上下限、自检词表 | 不得绕过 R4；不得写入事实清单外的信息 |
| `adapters/csdn/` | CSDN 操作 | 选择器、字段映射、步骤顺序 | 不得改 Adapter 七方法签名；不得在此写业务逻辑 |
| `core/session` | 登录态 | profile 路径、探活 URL | 不得存明文密码；不得自动重试登录 |
| `core/lock` | 幂等与并发 | 锁粒度 | **不得删除 `submitting` 中间态** |
| `core/guard` | 合规拦截 | 词表内容（L1） | 不得提供「跳过自检」开关 |
| `core/receipt` | 回执与回填 | 输出目录 | 不得改 `publish-log` 列语义（监测依赖） |
| `data/` | 存储 | 目录组织 | 不得改字段含义 |

### 9.3 逐需求影响矩阵

| 需求 | 改动会波及 | 不可动摇的部分 |
|---|---|---|
| R1 资料解析 | R3 正文内容、R4 数字校验 | 「无出处不进稿」，不可放宽 |
| R2 问句锚定 | R3 全文结构 | 一稿只能锚一个问句 |
| R3 成稿结构 | R4 自检项、平台字数限制 | 结论前置段不可移除 |
| R4 合规自检 | R7 / R8 能否放行 | 不得增加「跳过自检」参数 |
| R5 封面 | R7 上传环节 | 尺寸从平台读取，不得硬编码 |
| R6 登录态 | R7–R10 全部 | 登录失效只停不重试 |
| R7 草稿投递 | — | 未验证正文前不得点发布 |
| R8 全自动发布 | R10 回执 | 不得跳过 verify 直接算成功 |
| R9 幂等 | R8 重发判定 | 不得删除 `submitting` 态 |
| R10 回执 | R11 回填 | 列语义不可改 |
| R11 监测回填 | `geo-monitor` 全量 | 共享域名不得当自有域名 |
| R12 失败诊断 | — | 失败截图不可省略 |
| R13 风控即停 | 全部流程 | **不得出现任何验证码处理代码** |
| R14 节奏控制 | R8、R16 调度 | 阈值可调，逻辑不可绕过 |
| R15 产品库 | R1–R3 素材、R17 选题 | 事实必须带原始出处，不得凭空生成 |
| R16 每日调度 | R8、R14、R18 | 失败必须落日报，不得静默 |
| R17 选题串联 | R3 成稿方向 | 只能消费 gap_prioritizer 输出，不得自建排序 |
| R18 日报 | 用户验收 | 四问必须齐，缺一即不合格 |

### 9.4 你自己就能改的（不需要找我）

- 发布时间表、单日上限、平台错峰（R14 / R16）
- 标签集合、分类、封面尺寸提示
- 自检词表增删词
- 稿件字数上下限
- 选题翻新周期（R17 的 30 天约束）
- 输出目录位置
- 平台字数/标签上限
- 产品库增删产品与资料

### 9.5 必须找我、且要先评审的

- 加新平台（L2→L3 混合，需确认 adapter 签名是否够用）
- 改 `publish-log` 字段（监测依赖它）
- 改幂等状态机
- 改闸门规则（draft / publish / dry-run 的定义）
- 动 `geo-monitor` 的 `owned_channels` 结构
- 任何「临时放宽自检」的需求

> **关于「临时放宽」的边界**：R4 自检和 R13 风控这两处不设临时开关。理由是它们拦的是不可逆后果——发出去的错稿收不回来，被限流的号养不回来。这类需求不进配置层，写死在代码里。
